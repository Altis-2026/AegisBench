# AegisBench released results

Every number in the paper comes from one of the files below. Nothing here
is hand-edited: all four tables are regenerated by

```
python scripts/workshop_tables.py
```

from the raw sweep records in `results/sweep/`, and the paper build
(`make -C paper/cv4eo`) fails if any printed value disagrees with them.

## Conventions used in every file

| Field | Meaning |
| --- | --- |
| `recall`, `precision`, `f1` | Point estimates on the full test split, at the model's frozen operating point. Not bootstrap means. |
| `recall_ci_lo`, `recall_ci_hi` | Bootstrap percentile 95% interval, 1000 resamples **of images**, not of instances. |
| `conf_thresh` | The confidence threshold selected once on that checkpoint's own clean validation data by maximising F1, then frozen across all 28 conditions for that model. |
| `severity` | `0` for `clean`, otherwise `1`, `2` or `3`. |
| `n_gt`, `tp`, `fp` | Annotated persons, true positives and false positives at the frozen threshold. |
| `map50`, `map50_95` | Threshold-independent, so these are what settle whether a zero recall is a missing detection or a misplaced operating point. |

Matching is greedy and score-ordered at IoU >= 0.5, class-agnostic, run
by one shared evaluator for all three architectures, against
full-resolution ground truth after tiles are remapped and merged.

A recall of exactly `0.0` with the interval `[0.0, 0.0]` is not a
placeholder or a failed run. It means no annotated person in the split
was recovered, so every bootstrap resample also returns zero and the
interval is degenerate by construction.

## Files

### `benchmark_168_conditions.csv` (168 rows)

The headline grid: 3 detectors x 2 datasets x (1 clean + 9 corruptions x
3 severities). One row per condition. This is the table to read first,
and the one to cite if you want a single number for a specific
model/dataset/condition.

Key: `(model, dataset, corruption, severity)`.

### `mitigation_sard_lowlight.csv` (84 rows)

Before and after low-light augmentation on SARD, for all 28 conditions
per detector, so the cost of the intervention on conditions it was not
trained for is visible alongside the benefit.

`trained_on` is `yes` only for `low_light` severities 1 and 2, the two
conditions the augmented training set contained. **Severity 3 was held
out of training** and appears only at evaluation, so the severity-3 rows
measure generalisation along the ladder rather than recall of a trained
condition.

`conf_thresh_before` and `conf_thresh_after` differ for two of the three
detectors. Each mitigated checkpoint has its threshold re-selected on its
own clean validation data by the same rule as every other model; it does
not inherit the baseline's threshold.

Key: `(model, corruption, severity)`.

### `multiseed_sard_yolo11.csv` (84 rows)

Three independent SARD YOLOv11 training runs (seeds 17, 42 and 123),
each trained and threshold-selected separately under the identical
protocol, swept over all 28 conditions. Seed 17 is the run used
everywhere else in the paper.

Key: `(seed, corruption, severity)`.

### Raw records

`master_ci_seeds.csv` and `ci_seeds.csv` are the unprocessed sweep and
bootstrap outputs for the multi-seed arm, in the same column shape as
`results/sweep/master_ci.csv` and `results/sweep/ci_sard.csv`. They carry
the run timestamp, the git commit, the config hash and recall split by
COCO area band. Use these if you want to audit something the summary
tables drop.

## Reproducing

The corrupted imagery is not redistributed. It regenerates
bit-identically from the source HERIDAL and SARD releases, because every
stochastic element is seeded from a stable hash of image identity,
corruption, severity and global seed. The corruption parameters are in
`configs/corruptions.yaml` and the training configurations that produced
each checkpoint are in `configs/`, at the settings that produced these
numbers.
